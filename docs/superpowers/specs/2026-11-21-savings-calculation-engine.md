# 独立储蓄计算引擎重构设计

## 目标

将储蓄计算器拆成资产取数与计算两部分。纯 Python 引擎接收明确的起始月份、初始活期余额、初始存款和收支配置，在相同输入下得到可重复验证的结果。

## 当前问题

- SavingsCalculator 直接依赖 Django ORM 和 FundRecord，在构造时查询存款，在首月计算时再次查询活期金额。
- is_authenticated 同时决定起始日期和取数方式，计算所用时间隐含在 datetime.now() 中。
- calculate() 仅清空结果，没有恢复已被修改的存款队列。
- 已用同一实例重复运行 40 个月的样例复现状态污染，首次末月总额为 401440，第二次为 791440。
- 现有三个测试仅检查年龄段查找，缺少到期、转存、现金流与真实入口回归。
- 结果页在没有结果时从 get_context_data 返回重定向对象，存在无法正常渲染的路径。

## 推荐方案

沿用现有计算类，把 Django 取数与起始日期决策移到 savings_calculator.inputs。视图负责读取表单、准备输入、调用引擎和写入会话。引擎的模块导入和计算均可在未配置 Django 的 Python 进程中运行。

相比只把 ORM 查询包进一个工具函数，显式输入能同时隔离数据库、登录状态和当前时间。现有视图及模板继续使用原字段和路由。

## 输入与输出

- 引擎接收 basic_params、age_range_params、start_date、initial_current_amount、initial_deposits。
- 初始存款沿用当前四元组结构，包含开始日期、到期日期、本金和到期金额，金额使用 Decimal。
- Django 输入准备模块在登录模式下读取全家 ACTIVE 资产，按当前 ORM 公式和分组方法准备初始存款，活期余额仅汇总 CURRENT。
- 游客模式使用表单中的活期金额，初始存款为空，从最早收支年龄段对应年份的 1 月开始。
- 登录模式从传入的本地日期所在月份开始，默认日期在 Django 层按 Asia/Shanghai 获取，调用方可传入固定日期验证。
- 月度结果与摘要的字段名、会话结构和展示类型兼容现有页面。内部现金流继续使用 Decimal。

## 本阶段算法约定

- 收支区间重叠时沿用列表中第一个匹配区间。
- 年龄不在配置区间时，收入为零，支出取距离最近的区间。
- 年龄达到 80 岁停止生成月度结果。
- 保留指定月份年度支出、活期保留阈值、整万元转存、三年定存和单利计算规则。
- 初始资产的类别、状态、利率和存期筛选沿用当前取数口径，先用回归测试固定实际行为。
- 已有记录缺少开始日期等边界纳入验证，无法按现有规则计算时提供明确错误，具体回退不得静默改变本金或利息。
- 初始输入复制保存，每次 calculate() 从同一初始存款队列重新开始，调用方提供的字典和列表不被计算过程修改。
- 首次计算的月度结果保持现有算法，修正重复调用造成的状态污染。
- 无结果的会话或空结果正常重定向到输入页并显示提示。

## 修改范围

- savings_calculator/calculator.py 移除 ORM、登录状态和当前时间依赖，保留现有计算方法及结果契约。
- 新增 savings_calculator/inputs.py 准备资产快照和起始日期。
- savings_calculator/views.py 接入明确输入，处理结果缺失的重定向。
- savings_calculator/tests.py 及必要的新测试覆盖纯引擎、输入准备与实际页面。
- README 和本阶段实施记录同步更新。

## 验收

1. 未配置 Django 的 Python 进程可以导入并运行计算引擎。
2. 固定日期、配置和初始资产后，首月、年度支出、到期转存和三年到期月份符合回归样例。
3. 同实例重复计算、先计算部分月份再计算全部月份，与新实例的相同输入结果一致。
4. 保留现有年龄段边界与家庭资产共享口径。
5. 游客、登录成员和结果缺失入口均有请求测试，原有资金权限与 CSV 回归通过。
6. 独立 MySQL 测试容器执行全套测试和真实 HTTP 冒烟检查后交付。
